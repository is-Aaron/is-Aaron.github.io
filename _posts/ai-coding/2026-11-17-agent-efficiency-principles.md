> **核心观点**：Agent 的能力上限由模型决定，实际产出由它所处的环境决定。提效的关键不是把提示词写得更用力，而是把环境设计好：给对信息、定清目标、建好反馈、管住边界、持续改进。下面 12 条准则最终服务于同一个目标：**把人的注意力留给判断和决策**。

---

## 一、为什么讲准则，不讲技巧

Agent 工具迭代很快，技巧很容易过时。曾经要手动管理的上下文，现在会自动压缩；曾经要大写强调的指令，现在平铺直叙就能被遵守。

不变的是环境的作用。OpenAI 有个团队用 Codex 从零构建了一个百万行代码的产品。项目早期进展比预期慢，原因不是 Agent 能力不够，而是环境描述不足：缺工具、缺抽象、缺结构。团队的主要工作因此变成了**让 Agent 能把活干好**。

所以 Agent 提效本质上是一个环境设计问题。12 条准则描述的，就是一个好环境应该具备的性质。

## 二、准则速览

| 分组 | 回答的问题 | 准则 | 一句话 |
|------|-----------|------|--------|
| **信息** | 给 Agent 什么 | 1. 聚焦 | 一个 Agent 只做一件事，只给必需的信息 |
| | | 2. 可见 | Agent 看不到的东西等于不存在 |
| **目标与反馈** | 往哪走，怎样算到 | 3. 意图先行 | 先定义“做什么”和“怎样算完成” |
| | | 4. 闭环 | 不能验证的“完成”不算完成 |
| **约束** | 怎么管 | 5. 硬约束靠机制 | 底线交给系统，偏好交给 Agent |
| | | 6. 约束边界，不管细节 | 人管不变量，边界内放手 |
| | | 7. 风险与自主度相匹配 | 可逆的放开，不可逆的把关 |
| **协作** | 怎么分工 | 8. 隔离与共享分层 | 执行环境隔离，公共资产共享 |

每条准则下面都附有**自查**问题，用来判断自己有没有做到。

---

## 三、信息

### 1. 聚焦：上下文是稀缺资源

> 一个 Agent 只做一件事，只给完成这件事必需的信息。信息越多，注意力越分散。

研究发现了“上下文腐化”（context rot）现象：上下文越长，模型准确利用其中信息的能力越弱。Anthropic 因此把上下文工程的目标概括为：**用尽可能少的高信号 token，最大化得到期望结果的概率**。

上下文窗口变大并不能解决这个问题。窗口装得下，不代表模型能用好；而且每轮请求都会带上全部历史，无关信息会持续消耗成本。

**自查**：一个会话里是否混着几件不相关的任务？常驻规则是否大多与当前任务无关？

### 2. 可见：Agent 看不到的东西等于不存在

> 口头约定、个人经验、聊天记录里的决定，都要沉淀成 Agent 能读到的形式。

OpenAI 的说法是：Agent 运行时访问不到的知识，对它来说就不存在。只存在于文档系统、聊天记录和人脑里的决定，Agent 无从知晓，就像三个月后才入职的新人无从知晓一样。

这条与准则 1 不矛盾：准则 1 管**常驻什么**，准则 2 管**能找到什么**。两者的结合点是**渐进披露**：入口保持简短，像一份目录；深层知识等需要时再读。

边界也要清楚：**Agent 能从代码里读出来的，就不必再写**。需要沉淀的是代码里读不到的东西：决策背景、隐含约定、有误导性的历史遗留，以及已经纠正过两次的错误。

**自查**：同一个事实，Agent 是否每次都要重新摸索？同一个错误，你是否纠正过不止一次？

## 四、目标与反馈

### 3. 意图先行：先定义“做什么”和“怎样算完成”

> 人负责目标和验收标准，Agent 负责执行。

Agent 做偏，很多时候不是能力不足，而是缺少只有你才知道的信息，比如范围、取舍、偏好。缺了这些，它往往按最保守的理解来做。

所以分工的界线是：**“做什么”和“怎样算完成”由人定，“怎么做”交给 Agent**。如果自己还没想清楚，可以先让 Agent 反过来向你提问，把模糊的想法整理成一份明确的规格。这份规格也是后续验收和评审的依据。

**自查**：开始之前，能否用一两句话说清“完成”的标准？

### 4. 闭环：每项工作都要有可验证的反馈

> Agent 能自己判断对错，才能自己迭代。不能验证的“完成”不算完成。

Agent 在“看起来完成了”的时候就会停下。如果没有能返回“通过/失败”的检查，“看起来完成”就是它唯一的依据。这时**人就成了测试套件**，错误只能等人碰巧发现。

有了检查，Agent 就能自己走完“修改 → 验证 → 修正”的循环，不需要人盯着。验收时要**看证据，不看结论**：“都通过了”这句话本身说明不了什么，实际执行的检查及其结果才算数。

**自查**：Agent 说“完成了”之后，你是否还得自己再验证一遍？

## 五、约束

### 5. 硬约束靠机制，软偏好靠引导

> 必须遵守的规则交给系统强制执行，可以灵活处理的交给 Agent 判断。不要靠反复强调来保证执行。

| 类型 | 载体 | 效果 |
|------|------|------|
| **引导**（非确定性） | 提示词、规则文件 | 模型通常会遵守，但不保证 |
| **机制**（确定性） | 钩子（hook）、权限规则、CI、分支保护 | 由系统执行，每次都生效 |

大多数规则都有例外，模型面对具体代码时，往往比预先写好的规则判断得更好。所以**大部分规则留给 Agent 判断**，只有“绝不能发生”或“每次都必须发生”的少数事项才做成机制。

判断信号：**一条规则反复强调后仍会被忽略，就该改成机制**；反过来，只是个人偏好却被做成了机制的，应该删掉。机制宜少，因为每一条都可能误伤，也都需要维护。

**自查**：有没有一旦违反就无法挽回的底线，却只写在文字说明里？

### 6. 约束边界，不管细节

> 人只管架构边界和不变量，边界内放手让 Agent 自主发挥。

OpenAI 的做法是：**强制不变量，不微观管理实现**。比如要求数据在进入系统的边界处必须解析和校验，但不规定用哪个库。

这和管理大型工程组织是一个道理：**集中管边界，局部给自治**。边界写成可自动检查的规则后，能同时作用于所有代码；如果细节都靠人逐一指定，人马上就成了瓶颈。代价是产出未必符合个人风格，但只要正确、可维护、后来的 Agent 能读懂，就算达标。

**自查**：你的介入主要在边界上，还是在“怎么写”上？

### 7. 风险与自主度相匹配

> 可逆的操作放开，不可逆的操作把关。自主度越高，越需要权限边界、止损机制和最终签字人。

每一步都要人批准，看似安全，但批到第十次，人就开始不看内容直接同意。完全放开，又只适合随时可以丢弃的环境。合理的做法是**按可逆性分级**：读取和本地修改放开；删除、发布、对外推送、涉及敏感数据的操作必须把关。

Agent 无人值守地运行越久，人中途纠偏的机会就越少。因此开跑之前要先回答五个问题：完成的定义是什么？它能自己验证吗？它能动什么？什么时候必须停？结果由谁签字？

**自查**：无人值守的任务有没有止损上限？最终结果有没有明确的签字人？

## 六、协作

### 8. 隔离与共享分层

> 执行环境互相隔离，互不干扰；知识、规范和基础设施统一共享，避免每个 Agent 重复建设。

多个 Agent 并行时，冲突来自共享了不该共享的东西：同一个工作目录、端口、数据库或文件。反过来，规范、知识、工具和依赖缓存如果每个 Agent 各维护一份，又会造成重复建设和不一致。

| 层 | 内容 | 原则 |
|----|------|------|
| **共享层** | 知识、规范、工具、依赖缓存、基础设施 | 一份，大家复用 |
| **隔离层** | 工作目录、分支、端口、数据库、运行时状态 | 每个 Agent 各一份 |

一句话：**任务运行中会被改写的状态要隔离，跨任务复用的资产要共享**。拆分任务时沿模块边界切，避免两个 Agent 修改同一处。

**自查**：并行的 Agent 之间是否互相覆盖过？每开一个新 Agent，是否都要重复准备同样的东西？

### 9. 独立制衡：写的和审的分开

> 评审方不应受生产方思路的影响，否则只能起到复读作用。

看过实现过程的评审者，容易被同一套推理说服。**没看过实现过程的评审者**，才能提供独立的视角。

两点注意：

- **独立带来的是新视角，不是更强的能力**。让同等能力的 Agent 把任务重做一遍，结果不会更好。
- **评审要有依据**。对照规格检查需求是否实现、边界情况是否覆盖，比泛泛地“找问题”更有效。被要求找问题的评审者总能找出点什么，如果每条都改，只会让代码多出不必要的抽象。

**自查**：评审者是否和作者共用同一段上下文？评审有没有明确的依据？

## 七、演进

### 10. 持续治理：对抗熵增

> Agent 会放大已有的模式，好的坏的都会复制。所以要持续、小步地清理问题，不要等问题积累后再集中处理。

Agent 会模仿代码库里已有的写法，包括不好的写法。产出越快，代码库偏离规范的速度也越快。

OpenAI 那个团队起初每周五花一整天（约 20% 的时间）手工清理 AI 生成的低质量代码，但这种做法无法随规模扩展。后来他们把团队品味写成少量可机械检查的“黄金原则”，让后台任务定期扫描偏差、提交小修复，类似**垃圾回收**。技术债像高息贷款，持续小额偿还比攒到一起集中偿还便宜。

**自查**：清理是持续小步进行，还是攒到一起集中突击？

### 11. 失败即信号

> Agent 做不好时，不要怪它“不够努力”。要问缺了什么能力、信息或约束，补到系统里，让问题不再出现。

OpenAI 那个团队遇到失败时，几乎从不靠“再努力一点”解决，而是追问：**缺了什么能力？怎样让它对 Agent 既可读、又能强制执行？** 这样，一次性的纠错就变成了系统的永久改进。

常见失败大多能对应到前面某条准则：

| 失败表现 | 可能的缺口 |
|----------|-----------|
| 做的不是想要的 | 意图不清（准则 3） |
| 说完成了其实没有 | 缺少闭环（准则 4） |
| 反复犯同一个错 | 知识不可见（准则 2），或约束不够硬（准则 5） |
| 越做越乱 | 上下文混杂（准则 1），或熵增（准则 10） |

同一个问题纠正两次还不对，与其在已被污染的上下文里继续纠正，不如**把经验补进系统，从干净的状态重来**。

**自查**：每次失败之后，系统里有没有留下一点改进？

## 八、总目标

### 12. 人的注意力是唯一瓶颈

> 所有设计都要围绕一个目标：把人的时间留给判断和决策，不浪费在搬运和盯梢上。

代码可以大量生成之后，稀缺的就不再是代码，而是人的时间和注意力。在 OpenAI 的这次实践中，代码吞吐上去以后，瓶颈转移到了人工 QA。

前 11 条都是这一条的展开：

- **信息与目标（1–4）**：减少反复解释、纠偏和亲自验证；
- **约束（5–7）**：人只在底线和高风险处出现；
- **协作（8–9）**：并行不打架，评审不靠人逐行看；
- **演进（10–11）**：让系统自己变好，而不是靠人救火。

人的角色因此从“写代码”转向“设计环境、定义意图、构建反馈回路”。

---

## 结语

Agent 提效，不是让 Agent 更努力，而是让环境更好：

- 给它**恰好够用**的信息、**清楚的终点**和**自我检查**的手段；
- 用**机制**守住底线，在**边界内**放手；
- 让执行**隔离**、资产**共享**、写审**分离**；
- 把每次失败都变成系统的一次**升级**。

工具会变，这些准则回答的问题不会变：**当执行变得廉价，人的注意力应该放在哪里**。

## 术语表

| 术语 | 说明 |
|------|------|
| **Agent** | 在循环中自主调用工具完成任务的 LLM 系统 |
| **上下文（Context）** | 模型每次推理时看到的全部内容，包括系统指令、工具定义、对话历史、读取的文件等 |
| **上下文工程** | 决定每一步给模型看哪些信息的工程实践 |
| **上下文腐化（Context Rot）** | 上下文越长，模型准确利用其中信息的能力越弱的现象 |
| **渐进披露** | 先给简短入口，需要时再逐层加载更深的信息 |
| **Harness** | 包裹模型的运行框架，负责工具调用、权限、钩子、上下文管理，即 Agent 的工作环境 |
| **钩子（Hook）** | 在 Agent 运行的固定时机（如编辑后、结束前）由系统自动执行的脚本 |
| **不变量（Invariant）** | 无论实现怎么变都必须成立的约束，如依赖方向、数据校验要求 |
| **熵增** | 缺少维护时系统自发趋向混乱，这里指代码风格和架构的逐渐漂移 |
